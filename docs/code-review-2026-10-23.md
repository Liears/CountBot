## 2. 审查发现的缺陷（均已修复）

### 缺陷 1：IM 插话消息从未落库 —— 用户的话会凭空消失

**位置**：`channels/handler.py` 会话忙分支

原实现：会话忙时把消息写进内存收件箱后直接 `return`。而 `_save_message` 调用在该分支之后，永远执行不到。后果是：

- 这条消息**只存在于内存队列**，从未进数据库；
- 即使被当前轮合并进上下文，下一轮从数据库重建历史时它就消失了；
- 若当前轮异常退出，消息彻底丢失，用户看到的是「说了话没反应」。

**修复**：登记插话前先落库。同时引入 `_persisted` 标记，避免补救流程重新投递时重复写库。

### 缺陷 2：插话内容被当成助手回复回显给用户

**位置**：`agent/loop.py` 插话注入点

原实现 `yield f"\n\n{injected}\n\n"`，把用户补充的话送进了**助手输出流**。后果：

- 用户会在聊天窗口看到「助手在复述自己刚说的话」；
- 该内容会随 `response` 一起写入数据库，成为一条 assistant 消息；
- 产出一份错乱的对话记录。

**修复**：插话只进 `messages`（模型上下文），不进输出流；并加一句说明前缀，让模型知道这是用户补充而非自己说过的话。

### 缺陷 3：迭代额度被就地改写，额度提示失真

**位置**：`agent/loop.py` 额度检查

原实现为避免插话被额度耗尽丢弃，直接 `runtime_max_iterations = iteration + 1`。这污染了三处后续判断：工具调用额度、警告文案里的数字、循环条件本身。而且 `injected_turns` 只增不减，一旦发生过插话，之后每轮都能无限放宽。

**修复**：引入独立的 `iteration_budget` 作为循环条件，额度放宽只用一次（`grace_turn_used` 标记），原始配置值不被修改。

### 缺陷 4：排队消息无人消费时会永久滞留

**位置**：`session_gate.py` + `channels/handler.py` finally

插话的消费点只在「工具批次全部执行完之后」。如果本轮走了 `direct_result_selected` 直接返回、被用户取消、或抛异常，插话就没人取。消息留在内存字典里，既不会处理也不会清理。

**修复**：新增 `drain_pending()`，在 finally 中把未消费的消息重新投递回消息队列，作为独立的新消息处理。投递前清理 `_stream_handler` 等残留回调，避免复用已失效的发送句柄。

### 缺陷 5：exec 输出落盘异常未兜住

**位置**：`tools/shell.py` `_truncate_with_artifact`

`_write_output_artifact` 内部有 try/except，但一旦被替换（或未来改动）抛错，异常会直接冒泡导致整个 exec 工具失败——为了一个「锦上添花」的功能把主功能搞挂。

**修复**：调用处再加一层保护，失败退化为普通截断。

## 3. 覆盖缺口（已补齐）

### 用量统计只覆盖主循环

审查前只有 `loop.py` 记录用量。实际消耗还包括：

| 来源 | 文件 | 审查前 | 现状 |
|------|------|-------|------|
| 主对话 | `agent/loop.py` | ✅ | ✅ |
| 子代理 / 团队工作流 | `agent/subagent.py` | ❌ | ✅ 记为 `subagent` |
| 溢出历史摘要 | `session/context_service.py` | ❌ | ✅ 记为 `summary` |
| 整会话沉淀 | 同上 | ❌ | ✅ 记为 `summary` |
| 短期上下文摘要 | 同上 | ❌ | ✅ 记为 `compaction` |

**为什么重要**：团队工作流会并行跑多个子代理，其消耗占比可能超过主对话。不记录会系统性低估成本，让「注入开关省了多少 token」这类判断失真。

顺带修复：`usage_recorder` 未重新导出 `USAGE_KIND_*` 常量，`subagent.py` 导入会直接报 `ImportError`。

## 4. 健壮性验证

新增 `tests/test_session_gate_integration.py`，专门验证容易出事的状态路径：

| 场景 | 结果 |
|------|------|
| SSE 生成器被 `aclose()`（客户端断开） | 闸门正确释放，后续请求可进入 |

## 5. 待决项（未改动，需你判断）

### 5.1 cron / CLI 路径未接入闸门

`process_simple()`（`loop.py:1006`）直接调 `process_message`，不经过会话闸门。定时任务若与用户对话撞在同一会话，仍可能并发。

**未改原因**：cron 的 `session_id` 由任务配置决定，强行串行可能让定时任务因为用户正在对话而延迟或失败，属于产品行为变更，需要你先确认期望语义。

### 5.2 会话忙时网页端没有反馈

IM 渠道现在会静默排队（消息进队列，等本轮结束由补救流程处理），用户侧没有「已排队」提示。网页端 WS 路径是直接 `await` 闸门，前端会一直等到轮到自己。

**未改原因**：需要前端配合加提示 UI，属于交互改动。

### 5.3 `PendingMessage` 无过期机制

若极端情况下补救流程也失败（消息队列投递异常），排队消息会一直留在内存。当前有 `drain_pending` 兜底，且只在异常路径触发，风险很低；但严格说缺少 TTL 清理。

## 7. 是否真的有用

按价值排序：

1. **会话串行**——修的是正确性问题。审查中发现的 4 个缺陷都出在这块，说明它原本是「看起来能用、实际会丢数据」的状态。现在 IM 连发消息、网页多端同开都不会产生交错历史。
2. **请求预览**——直接消除「注入到底进没进」的排查成本。此前排查一个称呼问题用了三轮对话，现在一个接口就能看到 `dynamic_context` 的实际内容。
3. **用量统计**——让 token 优化有闭环。此前注入开关的价值只能估算，现在是实测数字。
4. **历史压缩**——原本是死代码（导入不存在的类），现在真能压缩，且切点保护避免了孤儿 tool_calls 导致的 400。
5. **exec 落盘**——小改进，但解决「长输出尾部看不到」的实际痛点。
